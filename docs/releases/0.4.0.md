# SaberOps v0.4.0

Released 2026-10-19. Preview software; interfaces, storage schemas and provider
integrations can change.

v0.4.0 changes what SaberOps is. Per
[ADR-0001](../decisions/0001-saberops-engine-mcp-first.md) it is now a
**headless, plan-aware execution engine**: tasks in, verified commits out,
through the vendors' official CLIs within each subscription's plan limits. The
chat/workspace application of v0.3.x is gone; the engine is driven through the
`orch` CLI, an MCP server and a local first-run web UI.

## Highlights

- **Jobs and pacing scheduler.** Durable job queue with requirements-only
  submission, priorities, deadlines and idempotency keys; a single-instance
  scheduler admits routes by verified billing posture and capacity, then picks
  by binding-window pacing score.
- **Plan registry, billing posture and capacity ledger.** Accounts, pools and
  usage windows; per-route posture classes with owner verification and expiry
  (unverified routes are never admitted unattended); learned per-job cost.
- **Quota preemption and resume.** Plan exhaustion commits work in progress to
  create-only checkpoint refs with a resume capsule and re-queues the job.
- **Role-chain routing.** Schema-3 routing with WORKER, SURGEON and INTEGRATOR
  fallback chains and Worker-to-Surgeon escalation; `orch routing migrate`
  converts older files.
- **Waves and lanes.** Deterministic wave/lane models, fail-closed admission
  with disjoint write scopes, sequential pinned-SHA merges, one gate per wave,
  the 3 projects × 5 child-task slot policy, and wave-plan scoring/optimization.
- **Gates.** Base-trusted gate profiles with candidate tamper protection, gate
  slots sized to free RAM, gate history, coverage-mapped affected gate, lane
  checks, failure attribution and a scheduled main gate.
- **Owner questions, unattended plans and Orchestrator memory.** Keyed question
  queue with five-part escalation; decision sheet, never-delegable list,
  circuit breaker, stall alarm and morning report; bounded startup digest,
  notebook, session lock and turn/rotation policy.
- **Project entry modes, roadmap change requests, central configuration** with
  an append-only owner decision ledger, and **`orch certify`** for dogfooding
  certification with nine resilience scenarios.
- **Storage lifecycle.** Owner-aware inventory, retention and guarded GC
  (`orch gc --dry-run|--apply`), host-wide storage reservations.
- **Security.** Worker isolation (worktree containment, Git control-surface and
  host-config protection, worker session authority), owner-only Review/Accept,
  hermetic allowlisted child environments, loopback `Host` allowlist.
- **Interfaces.** MCP server over stdio with 12 tools (`orch mcp`), complete
  first-run web UI, optional Telegram bot, and CLI parity with `--json` for
  reviewer/orchestrator/access/workflow/run operations.
- **Vendor CLIs.** Recorded real-CLI fixtures with a drift detector; pinned
  billing-relevant configuration for Codex and OpenCode; per-child OpenCode
  config isolation.

## Removed

- Chat and Work threads, the native console/session viewers and terminal web
  routes, the gateway package, authority sync and publishing modules.
- The Copilot worker adapter.
- Antigravity is attended-only and no longer part of automatic routing.

## Upgrade

```bash
git fetch origin --tags
git switch --detach v0.4.0
python3.12 -m venv .venv
.venv/bin/python -m pip install .
.venv/bin/orch --help
```

Back up existing state first. Stop any old `orch ui` process. Existing
databases gain additive tables when needed; old run policies stay frozen. Run
`orch routing migrate` to preview the role-chain migration of an older routing
file (`--write` persists it). Verify each route's billing posture with
`orch posture verify` before expecting unattended dispatch. A downgrade is not
a supported migration path.

## Validation

- `bash scripts/gate-full.sh` on the release tree: Ruff passed; strict mypy
  passed across 332 source files; 3,046 tests, 3,038 passed in the parallel
  pass and the remaining 8 passed on serial rerun (0 failed).
- Those 8 are `tests/test_gate_tools.py` tests that launch `main-gate.sh` and
  the exclusive gate-slot helper; under the gate's own 8-worker pass they time
  out on slot contention. The full-gate wrapper therefore reports them as
  unquarantined flaky tests (`GATE OUTCOME: FAIL`). This is a known
  test-isolation issue in the gate tooling, not in the engine, and is tracked
  for a follow-up fix. CI's serial `pytest -q` is unaffected.
- Tests and CI make no provider or model calls; vendor CLI behaviour is
  exercised through recorded fixtures.
