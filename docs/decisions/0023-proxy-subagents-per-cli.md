# ADR-0023: Proxy subagents in every orchestrating CLI

- **Status:** Accepted. Implemented by `orch connect --agents`.
- **Date:** 2026-11-19
- **Decider:** Saber (owner), Phase 1 plan lane F20
- **Related:** [ADR-0001](0001-saberops-engine-mcp-first.md),
  [ADR-0005](0005-mcp-first-engine-and-phase-2-board.md),
  [ADR-0024](0024-model-family-tokens.md)

## 1. Context

A native cross-vendor subagent is not available: Claude Code subagents use only
Claude models at the session endpoint, Codex agents inherit the parent's
provider, and Antigravity offers Gemini tiers only. Ask a CLI's own subagent
mechanism for another vendor and it cannot comply.

A **proxy subagent** is the cross-vendor route that exists. The host CLI shows
the delegation in its own subagent list; the proxy runs on the host's cheapest
model; its only action is a SaberOps `submit_job` carrying a model-family
requirement. The work then runs on the target vendor's own CLI and
subscription, and SaberOps keeps the job record, gate, independent review and
owner acceptance. The owner approved this path and asked for it on Claude Code,
Codex and Antigravity as well as OpenCode.

## 2. Decision

1. **Opt-in, one generated file per proxy.** `orch connect --agents` writes the
   definitions for each named CLI, or for all supported CLIs when none is
   named. `--dry-run` prints the exact path and content and writes nothing.
2. **Ownership is marker-guarded and reversible.** Every file carries a
   `saberops-managed-agent` marker and is written atomically. A file without the
   marker is never overwritten or deleted. `orch disconnect --agents` removes
   only marked definitions and keeps siblings.
3. **Targets follow the host, never its own subscription.** Claude Code gets
   `codex-worker` and `opencode-go-worker`; Codex gets `claude-worker` and
   `opencode-go-worker`; OpenCode gets `claude-worker` and `codex-worker`;
   Antigravity gets all three. There is never an `agy-worker`: SaberOps does not
   launch `agy` as an automated worker.
4. **Three unambiguous family tokens only.** Generated requirements use
   `anthropic`, `codex` or `opencode-go`. `claude` and `opencode` are not used
   because the matcher would also select a Go-hosted Claude model or every
   OpenCode provider. A proxy that is told "no eligible candidate" reports the
   reason and stops; it never retries another family.
5. **The session's server is referenced, never copied.** Each definition uses
   the `saberops` MCP server already connected to the host session. Starting a
   second server process would not share the session lease, so `submit_job`
   would be refused as read-only. Claude Code references the server in its
   agent frontmatter; Codex, OpenCode and Antigravity inherit the parent's MCP
   configuration.
6. **Host cost stays on the host.** Each definition names the host CLI's
   cheapest suitable model for the proxy turn. The proxy itself never edits
   files, runs shell or git, accepts, merges, pushes or approves billing, and it
   sets `caller_id="proxy:<name>"` for provenance only (the field is
   self-asserted, not authentication).
7. **The Go key is never embedded.** Nothing generated by this path reads,
   copies, prints or commits an API key; the proxy route needs none. Go remains
   reachable through the OpenCode worker, which uses OpenCode's own connection.

## 3. Consequences

- The owner can say "run this on Claude/Codex/OpenCode Go" inside any of the
  four CLIs and see the delegation in that CLI's own subagent list, without
  moving the main session off its subscription.
- A proxy is a native subagent: SaberOps cannot supervise, kill or quota-measure
  it. Closing the host CLI stops it silently, and its usage is the host's
  reported usage, not a SaberOps measurement.
- The route depends on the owner's build route containing a candidate for the
  requested family. Absent that, the honest result is "no eligible candidate",
  not a substitution.
- Antigravity may orchestrate and host these proxies but remains outside
  automated work and native Go.
